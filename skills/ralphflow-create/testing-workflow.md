# 测试工作流设计

当请求要构建测试任务，或要构建可复用的测试与缺陷工作流时阅读。交付物是一张工作图，其报告在发现缺陷或列出未验证范围时即属完整；你负责设计，用户负责启动。

## 梳理测试范围

设计前，先找到项目真正的检查入口：阅读 `package.json` 脚本、测试目录、CI 配置和现有测试数据。为每个验收区域记录：

- 全新的执行者能在 Git 工作树中运行的确切命令；
- 该命令读取的仅运行期数据或环境，例如未跟踪的 fixture、被忽略的测试数据目录；
- 该命令产生的证据：失败的测试名称、断言消息、用例结果、退出码。

覆盖区域来自任务的验收标准，而不是只看现有测试文件。没有任何命令检查的需求，要留在方案中，标为未覆盖并说明原因。

完成条件：每个区域都指明一条真实命令，或被记录为未覆盖并写明原因。

## 测试分支

Graph 始终在 Git worktree 中运行。为每条独立命令分配自己的 `background` 步骤；就绪步骤全部放行，由 DSH 的 agent 并发限制排队。

DO 在自己的工作树中用原生 Bash 运行命令，然后写入证据产物，记录确切命令、工作目录、退出码、输出摘要或节选，以及每个失败测试或用例及其断言消息。命令失败也是要记录的结果：当证据说明了实际发生的情况时，该分支即完成。

分支的 CHECK（独立验收）核验证据是否忠实：确切命令、真实退出码、每个被指名的失败及其证据、每个被指名的跳过及其原因。证据忠实的失败测试套件也能通过；这正是测试工作流的意义所在。

完成条件：每个分支都运行真实命令，并交付一个证据产物，其 CHECK 能接受失败或部分跳过的测试套件。

## 缺陷报告

一个综合节点依赖所有测试分支，并通过 `原生 read` 读取它们已验收的证据。它的报告合并三个部分：

- **缺陷**：每条发现单独一条记录，包含复现命令、退出状态、失败的测试或用例，以及它来自哪个证据产物。
- **覆盖情况**：一张表格，把每个计划中的验收区域归类为已验证或未验证，并附上证据或原因。
- **未验证范围**：每个缺失的数据文件、环境值、依赖或未覆盖区域，它导致哪项验收未验证，以及为什么没有验证。

测试全绿只是一种可能的结果，不是交付。交付是一份完整、有证据支撑的报告：当证据支持时，一份发现缺陷的报告同样完成任务。

完成条件：每个缺陷和每个计划中的验收区域都出现，并带有证据或明确的未验证原因。

## 缺失的资料

需要仅运行期数据或环境的命令，在 DO 里写清它读取的路径或条件，并让步骤先核对它们是否存在：

- 文件或目录：在任务文本或 DO 中给出工作区相对路径；缺失时把该步骤判为 blocked，并在证据中写明缺失路径和未验证范围。
- 宿主环境值：在 DO 中写明变量名和用途；缺失时同样 blocked，不编造值。

把缺失描述写成该资料提供的验收项，因为它会出现在状态和未验证范围中。没有已验收证据的计划验收区域，在报告中保持未验证。被跳过的关键验收永远不算通过。

完成条件：每个仅运行期输入都在 DO 中声明，由需要它的步骤核对，并描述为它所提供的验收。

## CHECK 的选择

- 测试分支：使用自定义 CHECK，判据覆盖可观察的证据——命令、退出码、被指名的失败和被指名的跳过。
- 报告：使用自定义 CHECK，判据覆盖证据引用、区域覆盖、未验证范围，以及“没有支撑证据就不得判定通过”的规则。按证据和覆盖情况评判报告，因此只要报告忠实记录，发现缺陷或指出被跳过的范围也算通过。
- 没有专门验收需求的节点可以关闭 CHECK。

完成条件：`ralphflow_doctor 的有效 CHECK` 显示每个节点选定的模式和判据，且报告判据能接受失败或部分跳过的测试套件。

## 交付

方案指明命令和已声明的资料；结果只有来自已验收的证据才能进入报告。交付的资产要固定其 CHECK 模式；设计期间不启动任何测试实例。用户在审查后明确启动工作流。
