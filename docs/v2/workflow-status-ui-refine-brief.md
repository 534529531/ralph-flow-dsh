# 工作流状态界面精修：一处常驻，只在该出现时出现

> 任务书是**目标书**，不是实现说明书（见 [brief-style.md](brief-style.md)）。
> 上一版任务书 `workflow-status-ui-brief.md`（已实现）建立了机制 —— 只读状态流、Typert 契约、
> 按会话绑定、恢复与隔离、两组负对照 —— **本版一条都不推翻**，只修它留下的两个用户侧后果：
> 同一件事说了三遍，以及新加的界面不像 dsh 自己的东西。

## 问题

上一版任务书写着「在当前 Chat 提供**可折叠状态卡与页头入口**」，判据 1 又要求「长对话滚动
仍能看见」与「原生审批接管时页头仍能打开详情」。三条合起来把实现者逼进了死角：卡片不能放
时间线（会被滚走）⇒ 只能进输入框上方；原生审批会接管输入区 ⇒ 页头必须再自带一份。结果：

1. **同一件事在界面上说了三遍** —— 页头一个徽标、输入框上方一张卡、时间线两条播报行。
2. **输入框上方常驻一大块**：稳态 3 行、展开 10 行，把对话区压掉。其中一段是常驻的
   **操作说明**（"无需操作：独立验证者正在取证判定，跑完会自动唤醒本会话继续。可用
   `/ralphflow-status` 看进度，`/ralphflow-cancel` 中止。"）—— 它自己都说了"无需操作"。
3. **它不像 dsh 自己的东西**：徽标带实心容器，卡片与弹层是手写阴影与圆角
   （`boxShadow: '0 6px 24px rgba(0,0,0,.14)'`、`borderRadius: 12`）。对照 dsh 自己的会话头
   控件（`dsh-client-ui-jobs`）：**裸文字 + 小圆点、无容器**，弹层走
   `--dsw-elevation-prominent` / `--dsw-specific-menu` / `--dsw-radius-lg`。
4. **终态不消失**：完成后只把一行文字换成"报告已归档"，卡片永远留着。
5. **内部数字进了 UI**：`本步未通过 0/100`（`loop.yaml` 的 `max_fail_count` 就是 100）。

用户原话：「我觉得好丑啊，而且为啥要上面显示后下面也要显示。」

## 目标

**用户随时知道工作流走到哪、什么时候需要他动手；界面上同一件事只有一处常驻位置；
新加的东西与 dsh 自身控件并列时，看不出是两家的。**

分工（本版的核心，也是上一版缺的那一节）：

| 位置 | 管什么 | 什么时候在 |
|---|---|---|
| **一处常驻**（对话滚动时仍在视口内） | 走到哪一步、在跑、还是在等你 | 永远；终态转成结果标记后收成最小形态 |
| **输入区一带** | **只在"需要你动手"时出现**：待放行 / 已暂停 / 失败到上限 | 只有那三种；处理完自行撤走 |
| **时间线** | 留痕、可回溯 | 永远（上一版已实现，保留） |

「常驻」是**一处**。上一版判据 1 的真实需求（滚动时仍能看见）由常驻位置自己满足，
**不需要再放第二份**；输入区那一份的存在理由是"需要你动手"，不是"更显眼"。

## 边界

1. **引擎仍是唯一事实源与推进者**：判定、验证者、投递分类、reset 时序、模型上下文一律不碰。
2. **只读状态流与 Typert 契约不动**：不新增 SessionEvent、不落盘派生相位、不加轮询或定时器；
   查看与展开不写会话事件、不开新回合。
3. **上一版的恢复与隔离语义全部保留**：按会话绑定、断线标记旧值、接管清卡、fork 不继承父会话、
   完成/取消只关联本会话自己的精确报告。
4. **上一版的两组负对照必须继续绿**：撤掉客户端 → 同一 DOM 断言失败；阻断推送 → 实时断言失败。
5. **不改宿主**：不动 dsh 本体的样式表与组件，只用公开的槽位与主题 token。
6. **时间线播报行不升级也不删除**：它是记录，不是状态面板。

## 完成判据

1. **恰好一处常驻**：有活跃工作流的会话里，承载"走到哪 / 在跑还是在等"的**常驻**位置
   恰好一处，且它在对话滚动时仍留在视口内。
2. **不占输入区**：`executing` / `verifying` 阶段，输入框上下的**常驻**占位为零
   —— 输入区只在判据 3 的三种状态里出现，离开那三种状态后自行撤走。
3. **要人动手时看得见、看得懂**：`gate` / `paused` / 失败到上限时，视线焦点附近出现一处提示，
   **一眼能看出要用户做什么**（一个动作，不是一段说明书）。处理后撤走。
4. **终态不长期占据**：`done` / `cancelled` 之后，常驻位置收成最小形态（结果标记 + 可取报告），
   输入区不得再出现任何东西；刷新后结果与报告路径仍可取。
5. **与 dsh 同源（可判定）**：新加界面**不得手写**颜色、圆角、阴影、字号 —— 一律走 dsh 主题
   token。取证两条：① 源码里 grep 不到硬编码的视觉常量（`boxShadow` / `borderRadius` /
   `rgba(` / 数值 `fontSize`）；② 与 dsh 自己的同类控件（会话头的 `job-list` 控件、输入区已有的
   goal 条）截图并列，看不出是两个产品。
6. **内部数字不进 UI**：`max_fail_count` 这类内部预算不作为默认展示（`0/100` 是噪音）。
   要表达进度就用用户能理解的说法（第几轮），只在接近上限时才提示 `n/m`。
7. **无实例不出现**：没有工作流的会话不出现任何空壳（沿用上一版判据）。
8. **回归**：`npm run build && npm run typecheck && npm run verify` 全绿；
   `node scripts/ui-status-web.mjs` 的真机验收按新判据更新后通过。

## 取证路径

- 真机：`node scripts/ui-status-web.mjs`（隔离 HOME / 工作区，真实 `dsh web` + 真实 AgentLoop +
  真实原生验证者 + Chat DOM）。按新判据补三张截图：`executing` / `verifying` 阶段输入区无占位、
  `gate` 或 `paused` 时的提示、`done` 之后的收束形态。
- 对照物（定义"dsh 自己的同类控件"长什么样）：`dsh-client-ui-jobs/lib/client.js` 的
  `Hcm_Iq_trigger` 与 `Hcm_Iq_menu`；`dsh-client-ui-goal` 的输入区条。
- 重复计数：`src/client/status.tsx` 的 `registerUi` 里数常驻注册点；时间线播报行单独数。
- 负对照：沿用上一版两组，外加一条 —— 把常驻位置撤掉后，判据 1 的"恰好一处"断言必须变红。

## 已知的坑

- **上一版的失败模式是任务书自己把 UI 组成写死了**（"可折叠状态卡与页头入口"）。本版只定
  「谁、在什么时候、说什么」，**不定组件、DOM、槽位与视觉细节** —— 那是实现者的活，
  也是它被验证的依据。若实现者发现某条判据只能用更笨的界面满足，先改判据再改代码。
- 时间线播报行与状态面板是**两种东西**：不要为了"随时看得见"把播报升级成常驻件，
  也不要因为有了状态面板就删掉播报。
- 改客户端需要**重启 `dsh web`** 才会被提供（客户端 bundle 是启动时扫 Loader 组图的）。
