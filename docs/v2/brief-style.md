# 任务书写作规范

> 给**作者**（写任务书的人）看。一页，别加长。

## 一条规则

**目标说清楚；有已验证的方案就一句带过；其余留给 loop。**

任务书是**目标书**，不是**实现说明书**。

## 为什么

写死实现方案会**收窄验证空间**：验证者只能核对「有没有按作者说的做」，而不是「目标有没有达成」。
裁判权就从独立会话手里被收回给作者了 —— 而裁判权在独立会话正是这个产品的中心定理。
**作者写得越细，验证越弱。** 这不是文风问题，是产品问题。

## 怎么写

| 该写 | 不该写 |
|---|---|
| 要达成什么、什么叫做成了 | 逐函数的改法、逐行的顺序 |
| 边界与不变量（不许动的东西） | 具体数据结构与算法选型 |
| 怎么取证、什么算失败 | 作者猜的实现步骤 |
| **确属必需**的硬约束（如「不得新增状态字段」），一句带过 | 把硬约束展开成三节论证 |
| 已验证的对标事实（一句 + 出处） | 抄一整段对标源码进任务书 |
| 已知的坑与反直觉点（防呆） | 复述常识、复述仓库已有的文档 |

**验收标准**写「可判定的结果」，不写「作者设想的做法」。

## 检查一下

写完自问：

1. 删掉所有「怎么做」，剩下的「要什么」还完整吗？不完整 → 目标没说清楚。
2. 验证者拿这份能不能**独立判断目标有没有达成**？只能判断「照做了没」→ 写太细了。
3. 有没有哪一节是在**替实现者思考**？删掉——那是它的活，也是它被验证的依据。
