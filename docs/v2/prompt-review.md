## 提示词与机制如何衔接

- DO 新增当前 input 和验收依据，执行者与验证者使用同一当前步定义；只展示当前步，不加载未来步骤正文。子工作流调用点 input 仍只作委托声明。
- reset 交接稿保持现算的工作流、步骤、产出目录与协议。spec 明确从 proposal/tasks/design 恢复已记录决定；没有新增状态字段或自动聊天摘要。
- 通用返工提示保留完整当前步要求，失败反馈只用于定位和排序。loop 仍按原有三票整体验收，不强制增加 tasks.md。
- 验证 persona 区分文档交付物与其中的完成声明；清单勾选须用实际产出核对。取证 scope 绑定既定要求，保持只读交付物，受限时明确证据缺口。
- CHECK 要求 reason 自包含判据、证据、阻塞项和修复目标，优先保留可供返工的信息；判定解析、结构化 schema 和 T1 隔离方式未改变。
- 独立验证和通知由引擎驱动。通知无需模型逐条回应，submit 结束当前回合；纯人工门交卷即停，独立验收门通过后停。
- no_submit 暂停后先 continue 恢复，再 submit；提示与真实拒绝暂停态交卷的规则一致。人工放行、暂停恢复、接管以用户指令为准。
- 创建时只修复目标定义的诊断项，范围外错误如实报告；不会为清空 doctor 全局错误而修改其它运行。

## 验证与局限

本地运行 build、typecheck、verify（28 支）；发布 Action 再用干净 npm 默认宿主依赖重复验证。重点包括原生 reset 后的输入与 DO、审查门/免验证、三票范围、交卷恢复、结构化与降级判定、独立取证和既有负对照。新契约测试实际打包并解包后读取参考路径，确认按需指针在安装布局可达。

这些证据验证提示组装、调用路径、发布资产和协议一致性，没有真实模型效果对照。跨步决定仍需执行者落盘；只读纪律不是 bash 沙箱；原始任务仍是验收范围，三票不能彻底消除模型误判。本次不新增执行相位、并发调度、机械文件门禁或停止协议。

[Ralph 一手项目对照](ralph-prompt-research.md)保留为研究记录：曾考虑的 loop 四段方案未采用；借鉴不等于成功率证明。最终发布范围以本文件及代码为准。
