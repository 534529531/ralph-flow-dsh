# 工作流 YAML 参考

创建指南指向的按需参考。字段行为以加载器及 doctor 的结果为准；这里只描述本插件支持的方言。

## 本版本支持的 YAML 方言（引擎硬校验）

下列为字段参考片段，示例中的目标 id 须在实际定义中存在；完整流程应从首步可达并有完成出口。

```yaml
description: 一行描述，显示在工作流列表里   # 可选，建议填

manual_step:            # 可选：停下等人放行的步骤 id（有检查依据（check / check_voting）→ 对抗验证通过后停；都没有 → 纯人工审查）
  - design              # 列表写法；也接受逗号字符串 "design,review"
                        # 必须是**工作流级**（顶层，与 steps 同级）；引用不存在的步骤 = 硬错误（门会静默失效，绝不放过）
                        # **步骤级 `manual_step` 键已删除**：写在步骤里（不论 true/false/空值）= 硬错误——
                        # opencode 只认这个顶层列表，步骤级写法会被当作未知步骤键忽略，人工审查门静默消失

adversarial_check:      # 可选：独立验证者配置（**只允许 model 一个字段**）
  model: deepseek/deepseek-chat   # 可选：验证模型。两种写法都行：
                        #   "provider/model" 字符串，或对象 { providerID, modelID }（两者都要填）
                        #   裸模型名（如 sonnet）解析不出 provider → 告警并回退发起会话当前模型
                        # 不写则验证者沿用发起会话当前模型；别的字段一律告警忽略，不生效
                        # 验证者身份/职责是 Ralphflow 内部定义，不需要也**不能**在 YAML 里配置
                        # 验证超时不在这里设置（交给宿主 dsh 的原生看门狗）

# auto_reset: true      # 可选（缺省 false）：**工作流级重置门** —— 等价于给**所有**步骤标 reset: true
                        # （任何方式进入都触发，含失败重试）。语义与步骤级 reset 完全一致，区别只在措辞。
                        # 纯线性流配它会每次失败重试都重置上下文，token 成本较高（doctor 会提示）。
                        # 必须是布尔值（写成 "true" = 硬错误）；工作流首步的初次进入同样无法重置。

steps:                  # 必填，非空；从第一个元素开始执行
  - id: step-id         # 必填，唯一
    desc: 一句话说明     # 必填：一句话步骤说明（会进 DO/CHECK 提示词；**空串算缺**）
    do: |               # 必填：主会话执行的 DO 指令（缺失/非字符串/空串 = 硬错误）
      完成实际工作…
    check: |            # 不在顶层 manual_step 列表里的步骤请务必填：独立验证者的取证判定配方
      检查…              # 与 check_voting 二选一；两者都不写 = 该步不做独立验证，DO 完成直接进入下一步
                        # 两者都不写而该步在 manual_step 列表里 = 纯人工审查（停门等你放行）
    # check_voting:     # 与 check 二选一（同写 = 硬错误）：多验证者投票，1-5 个验证者**并行**、
                        # 各查一条检查依据、**全过才放行**；任一票不通过 → 整体失败并聚合所有失败理由
                        # 现成例子：内置 loop 是需求与边界、实际可用性、回归影响三个互补视角
    #   - check: 用户任务的每一条要求都已落实
    #   - check: 实现的行为符合预期，真实可用
    #     model: deepseek/deepseek-chat   # 可选：该票专用模型（不填继承全局 adversarial_check.model）
    input: proposal.md  # 必填：输入说明（**进 DO 与 CHECK 提示词**；写清输入在哪里及如何使用）
    output: |           # 必填：交付物说明（只说**产出什么**；落在哪里见「产出目录」一节）
      实现的代码/文件
    on_pass: next-id    # 必填：下个步骤 id，或 "done"（末步）；不再有「缺省 = 顺序下一步」
    on_fail: step-id    # 必填：失败重试目标（步骤 id，**不允许 "done"**）；不再有「缺省 = 自身」
    max_fail_count: 3   # 必填：≥1 的整数失败预算；不再有「缺省 3」
    check_model: deepseek/deepseek-chat   # 可选：**本步**的验证模型，覆盖全局 model（写法同 model）
                        # 仅单 check 场景生效：与 check_voting 同写、或本步没有 check = 硬错误
    reset: true         # 可选（缺省 false）：**重置门** —— 进入本步前把会话可见面整段替换成一条
                        # 「交接稿」，模型收到的 messages = 系统提示 + 交接稿 + 本步 DO。
                        # 只在**步骤边界的空闲窗口**生效；工作流**首步**标了也无效（首步 DO 是启动
                        # 工具的返回值，替换会落在工具调用内部 → 静默损坏会话），启动回执会如实说明。
                        # 必须是布尔值：写成 "true" 这类字符串 = 硬错误（不静默当成 false）

  # ── 子工作流步骤：用 `workflow:` 代替 `do:`，整步委托给另一个工作流（可多层嵌套）──────
  #    可选 `do:` 写在调用点上 = 这段子工作流「要做什么」（下沉到子步骤的「## 任务」）
  - id: analyze         # 必填，唯一；**不能含 /**（展开后子步骤 id 是 `调用点id/子步骤id`）
    desc: 需求分析       # 必填：与子工作流各步的 desc 组合显示（`需求分析 · 子步骤 desc`）
    input: proposal.md  # 必填：调用点没有 DO/CHECK 阶段 —— 这一项只作为**委托声明**被保留与校验
    output: analysis.md # 必填：同上
    workflow: analyze   # 必填：子工作流**名**（`workflows/<名字>.yaml`、全局目录或内置同名）；不能是路径
    on_pass: build      # 必填：整段子工作流跑完后去哪（步骤 id 或 "done"）
    on_fail: analyze    # 必填：只做**引用校验**（子步骤失败不会回到它 —— 子步骤耗尽预算是暂停等人）
    max_fail_count: 3   # 必填：同上，只做校验
    reset: true         # 可选且**在调用点上生效**：进入子工作流 = 首个展开后子步骤的重置
    do: 把需求整理成 analysis.md  # 可选且**在调用点上生效**：这段子工作流「要做什么」= 子工作流的任务
                        # （下沉到它每个步骤的「## 任务」；不写就继承父级任务描述）
    # 调用点**接受并校验**：id / desc / do / input / output / workflow / on_pass / on_fail /
    # max_fail_count / reset（id / desc / input / output / workflow / on_pass / on_fail / max_fail_count **必填**，do 与 reset 可选且生效）。其余键（check /
    # check_voting / check_model / inputs / 未识别键）一律**加载期告警并指路**、不生效 ——
    # 它们都属于子工作流**内部**的具体步骤。
```

**验证模型优先级链**（与 opencode/claude 一致）：`check_voting` 条目 `model` > 步骤 `check_model` > 全局 `adversarial_check.model` > 发起会话当前模型（都不写时不传模型覆盖，由宿主继承发起会话的 provider/model）。

**硬规则**（违反 → 启动即被拒绝并说人话）：
- **六个步骤字段必填**：`desc` / `input` / `output` / `on_pass` / `on_fail` / `max_fail_count`。
  缺失、非字符串、**空串**都不接受（`desc: ""` 与没写等价）。理由不是对齐而是**静默**：这些字段
  在 opencode/claude 的加载器里缺一个就**静默丢步**（或整份拒收），资产会不再表示它所说的话。
  **子工作流调用点同样必填这六个**（那两家的加载器把这项校验排在第 `workflow` 分支之前）。
- `do` 必填且为非空字符串；唯一的例外是本步写了 `workflow`（子工作流调用点）——调用点上的 `do` **可选**：写了就是**这段子工作流的任务**（下沉到它每个步骤的「## 任务」），不写就继承父级任务描述。写成非字符串是硬错误。
- `check` 若出现必须是字符串：写了非字符串（如 `check: true`）是硬错误——否则它会被当成「未配置检查」而静默跳过验证。本意是跳过就直接删掉该字段。
- `check` 与 `check_voting` **互斥**，同写 = 硬错误。
- `check_voting` 必须是 1-5 条的数组，每条有非空的 `check`；空数组、超 5 条、条目缺 `check` 都是硬错误。
- `on_pass` / `on_fail` 必填，且必须引用存在的步骤 id（`"done"` 仅 `on_pass` 有效）。
- `manual_step` 只能是**工作流级**（顶层列表），且必须引用存在的步骤 id（**也可以写子工作流调用点的 id** = 整段子工作流跑完后停门）。步骤级 `manual_step` 键已删除：写在步骤里不论什么值都是硬错误（opencode 会把它当未知键忽略，人工审查门静默消失）。
- `max_fail_count` 必填，必须是 ≥1 的整数。
- `check_model` 与 `check_voting` 同写、或写了 `check_model` 却没有 `check`，都是硬错误。
- `reset` 若出现必须是布尔值（`reset: true` = 进入本步前重置上下文）。写成字符串（如 `"true"`）是硬错误——静默当成 `false` 会让作者以为上下文被清了、实际没清。**写在子工作流调用点上同样生效**（= 进入子工作流时、即首个展开后子步骤的重置）。
- 顶层 `auto_reset` 若出现必须是布尔值（`auto_reset: true` = 给所有步骤标 `reset`）。写成字符串同样是硬错误，理由同上。
- `steps` 非空，id 唯一。

**子工作流的加载期硬错误**（本实现刻意比 opencode 更早失败；那边这几条要么静默忽略、要么拖到运行到该步才炸）：`workflow` 不是非空字符串；`workflow` 名含路径分隔符；子工作流文件加载不出来或定义非法（错误里给出完整调用链）；**子工作流成环**（含自调用，错误里打印环的路径）；**嵌套深度超过 32 层**（含最外层；展开器是递归的，过深的链在展开前就被拒，绝不冒泡 RangeError —— 步数上限看不见「每层零步骤」的长链）；调用点 id 或子工作流步骤 id 含 `/`（展开用 `/` 组前缀，含分隔符会与展开结果撞名）；展开后步骤 id 撞名；**展开后步骤总数超过上限 2000**（展开过程中计数，超了立刻中止）。

**doctor 告警**（能启动，但会出问题）：不可达步骤（从第一个步骤沿 on_pass/on_fail 走不到）；没有任何可达步骤的 `on_pass: done`（工作流永远无法完成）；`{{...}}` 模板记号（本版本**不解析任何**模板变量）；**不在顶层 manual_step 列表里且既无 `check` 也无 `check_voting`** 的步骤（该步不会被独立验证，DO 完成后直接进入下一步——在 manual_step 列表里的这类步骤是纯人工审查，**不告警**）；`check_voting` 只有 1 票且没配 `model`（等同单验证者，建议直接用 `check` 或配多视角/多模型）；`auto_reset: true` 而所有步骤的 `on_fail` 都指向自身（纯线性流——每次失败重试也会重置上下文，token 成本较高）；`model`/`check_model`/投票条目的 `model` 解析不出 provider（裸模型名，或对象缺 providerID/modelID）——此时该配置被忽略并回退，**不会静默生效**；`adversarial_check` 不是对象、或写了 `model` 以外的字段、投票条目里写了 `check`/`model` 以外的字段——这些字段被忽略（不生效），错误照旧在加载期就报出来，不拖到验证阶段；**子工作流调用点上除 id/desc/do/input/output/workflow/on_pass/on_fail/max_fail_count/reset 以外的每一个键**（逐键告警 + 指路：告诉作者该写到子工作流内部的哪一层；`inputs` 会指路到调用点的 `do`）。

**输出契约**：output 列明最终产出与必须交接的过程文档；do 负责生成与更新，check 负责核对存在、内容及实际证据。output 本身不会创建文件或机械检查文件存在。过程文档列入 output 后仍遵循下方落点规则。

**产出目录**：每个实例有隔离的产出目录 `<workspace>/.dsh/ralph-flow/artifacts/<实例ID 摘要>/`（目录名 = 任务摘要 slug + 实例 id 尾段），实例启动时自动建好。它是**过程文档**（清单、方案、报告、摘要、草稿等）的唯一默认落点：`do`/`output` 里写**裸文件名**即可（例如 `summary.md`），不用写路径、也不需要任何模板记号；写了**明确路径**的按写的路径来。工作目录只放本步的**产物**（代码、资源、可执行文件）；同一份过程文档只写一处、不要在工作目录里再留副本。DO 与 CHECK 提示词都会自动带上这条落点边界（CHECK 还会点明「工作目录里的副本是落点错误、不算满足」）。

**实例生命周期**：工作流完成或取消时，实例目录与 `state.json` 会被**销毁**，最终报告归档到 `<workspace>/.dsh/ralph-flow/reports/<实例ID>.md`（报告与产出是永久的，插件永不自动删除；只有**空的**产出目录会被删掉）。要回看已结束的运行，用 `/ralphflow-list` 的「历史运行」节或直接读报告文件。

**子工作流（加载期静态展开，与 opencode 对齐但落地方式不同）**：调用点被**就地展开**成子工作流的步骤 —— 每个子步骤 id 是 `调用点id/子步骤id`（多层继续叠加，如 `analyze/research/step1`），子工作流的出口（`on_pass: done` ）接到调用点的 `on_pass`（调用点必须显式填写）。运行期因此没有任何「父子状态栈」：`current_step` 仍是单字符串、失败预算仍按步记账，**零新增实例状态字段**。要点：

- **失败预算归子步骤自己**：某个子步骤耗尽 `max_fail_count` → 工作流**暂停等你定夺**（绝不会自动走调用点的 `on_fail`）。调用点的 `on_fail` / `max_fail_count` 仍然是**必填项**（照抄 opencode/claude 的加载器顺序：那六项必填校验排在 `workflow` 分支之前），在本实现里只做**引用校验**、不参与运行。
- **审查门两种标法**：① 标在**子工作流内部**的普通步骤上（原样生效，id 前缀化）；② 标在**调用点上** = **整段子工作流跑完后停门**（映射到子工作流的出口步骤；opencode 禁止这种写法，这里是刻意差异）。
- **重置门**：`reset: true` 写在调用点上 = **进入子工作流时重置**（本实现的静态展开模型：进入子工作流就是进入它首个展开后子步骤）。子工作流的 `auto_reset: true` 会下沉到它的每一步。
- **验证模型逐字段继承**：子工作流的 `adversarial_check.model` 会**下沉到它各步的 `check_model`**（投票步则填进缺 `model` 的票）；子层没填（或填了但解析不出 provider/model）就回退父级，逐层向外。所以最外层统一配一次即可。
- **任务取自定义层**：调用点上写 `do: …` = 这段子工作流的任务（下沉到它每个步骤的 DO/CHECK 提示词「## 任务」）；嵌套时**最内层优先、外层继承**（内层调用点写了 `do` 就覆盖外层，没写就继承外层）。不写就回落父级任务描述 —— 与改造前逐字一致。
- **不传参**：`inputs` 不生效（调用点告警，并**指路到调用点的 `do`**）。要在调用点上说明这段子工作流要做什么，就写它的 `do`。
- **展开会复制**：同一个子工作流被 N 个调用点引用就展开 N 份（步骤数与验证次数同倍增长），计数上限 2000。

**本版本未支持**：`inputs`（子工作流传参）——出现在调用点上一律告警忽略并指路；其它未识别键同样告警忽略（**子工作流调用点是唯一例外**：调用点上不生效的键逐个告警 + 指路，绝不含糊过去）。
